## Завдання №1. Розрахунок та порівняльний аналіз трудомісткості операцій керування доступом (DAC vs RBAC)

### 1.1. Вихідні дані та аналітичні моделі оцінки трудомісткості

Згідно з методичними матеріалами лекції №14 («Керування повноваженнями доступу до БД в СУБД PostgreSQL» [1]), складність та трудовитрати адміністратора безпеки бази даних на налаштування та підтримку прав доступу визначаються кількістю зв'язків між суб'єктами, правами та об'єктами, які необхідно сконфігурувати командою `GRANT` (або скасувати `REVOKE`).

За умовою завдання вхідні параметри залежать від номера варіанта $n$:
- **Кількість таблиць (об'єктів доступу, $T$):** $T = n \times 3$
- **Кількість користувачів (суб'єктів доступу, $U$):** $U = n \times 4$
- **Кількість груп / ролей користувачів ($R$):** $R = n \times 2$

Для варіанта **$n = 13$**:
- $T = 13 \times 3 = 39$ таблиць;
- $U = 13 \times 4 = 52$ користувачі;
- $R = 13 \times 2 = 26$ ролей (груп).

---

#### Математичні моделі трудомісткості

1. **Модель DAC (Discretionary Access Control — Дискреційне/вибіркове керування):**
   У моделі DAC права призначаються безпосередньо кожному користувачеві індивідуально на кожну таблицю. Для надання доступу $U$ користувачам до $T$ таблиць потрібно виконати операції зв'язування «користувач — таблиця»:
   $$W_{\text{DAC}} = U \times T$$
   В аналітичному вигляді через параметр $n$:
   $$W_{\text{DAC}}(n) = (4n) \times (3n) = 12n^2$$

2. **Модель RBAC (Role-Based Access Control — Рольове керування доступом):**
   У моделі RBAC процес адміністрування розділений на два рівні абстракції:
   - **Permission Assignment ($PA$):** призначення прав доступу до таблиць ролям ($R \times T$ зв'язків). Ці правила не залежать від користувачів і формуються один раз під час створення ролі;
   - **User Assignment ($UA$):** включення користувачів до ролей ($U$ зв'язків при закріпленні користувача за його основною штатною роллю, $k = 1$).
   
   Загальна трудомісткість операцій керування для RBAC становить:
   $$W_{\text{RBAC}} = (R \times T) + U$$
   В аналітичному вигляді через параметр $n$:
   $$W_{\text{RBAC}}(n) = (2n \times 3n) + 4n = 6n^2 + 4n$$

> *Примітка:* Навіть у випадку, коли користувач у середньому бере участь у $k$ ролях ($k > 1$), доданок $UA = k \cdot U$ зростає лінійно, тоді як основна трудомісткість конфігурації таблиць залишається фіксованою на рівні ролей.

---

### 1.2. Розрахунок для базових умов ($n = 13$) та порівняння моделей

Підставимо значення для варіанта $n = 13$ ($T = 39$, $U = 52$, $R = 26$):

1. **Трудомісткість моделі DAC:**
   $$W_{\text{DAC}} = 52 \times 39 = 2028 \text{ операцій}$$
   *(Аналітично: $12 \times 13^2 = 12 \times 169 = 2028$)*

2. **Трудомісткість моделі RBAC:**
   - Налаштування прав для ролей: $W_{PA} = R \times T = 26 \times 39 = 1014 \text{ операцій}$;
   - Призначення користувачів до ролей: $W_{UA} = U = 52 \text{ операції}$;
   - Загальна трудомісткість:
     $$W_{\text{RBAC}} = 1014 + 52 = 1066 \text{ операцій}$$
     *(Аналітично: $6 \times 13^2 + 4 \times 13 = 1014 + 52 = 1066$)*

3. **Порівняння моделей:**
   - **Абсолютна різниця трудомісткості:**
     $$\Delta W = W_{\text{DAC}} - W_{\text{RBAC}} = 2028 - 1066 = 962 \text{ операції}$$
   - **Відносне співвідношення (у скільки разів RBAC ефективніша):**
     $$K_{\text{eff}} = \frac{W_{\text{DAC}}}{W_{\text{RBAC}}} = \frac{2028}{1066} \approx 1.902 \text{ раза}$$
   - **Зниження трудомісткості:**
     $$\delta = \frac{W_{\text{DAC}} - W_{\text{RBAC}}}{W_{\text{DAC}}} \times 100\% = \frac{962}{2028} \times 100\% \approx 47.44\%$$

**Висновок за п. 1:** Уже за базових параметрів використання моделі RBAC скорочує трудовитрати адміністратора на **47.44%** (майже у **1.9 раза**). Перехід на RBAC є доцільним, оскільки усуває дублювання призначення однакових прав десяткам окремих користувачів.

---

### 1.3. Повторний розрахунок для змінених умов ($U \times 2$, $R / 2$)

За умовою завдання №1 (пункт 2) виконаємо зміну параметрів системи:
- **Кількість користувачів збільшено у 2 рази:**  
  $$U_2 = 2 \times U = 2 \times 52 = 104 \quad (U_2 = 8n)$$
- **Кількість груп/ролей зменшено у 2 рази:**  
  $$R_2 = \frac{R}{2} = \frac{26}{2} = 13 \quad (R_2 = n)$$
- **Кількість таблиць залишається незмінною:**  
  $$T = 39 \quad (T = 3n)$$

#### Розрахунок трудомісткості у нових умовах:

1. **Модель DAC:**
   $$W_{\text{DAC}, 2} = U_2 \times T = 104 \times 39 = 4056 \text{ операцій}$$
   *(Аналітично: $8n \times 3n = 24n^2 = 24 \times 169 = 4056$)*  
   *Трудомісткість у DAC зросла рівно у 2 рази (з 2028 до 4056).*

2. **Модель RBAC:**
   - Налаштування прав для ролей: $W_{PA, 2} = R_2 \times T = 13 \times 39 = 507 \text{ операцій}$;
   - Призначення користувачів до ролей: $W_{UA, 2} = U_2 = 104 \text{ операції}$;
   - Загальна трудомісткість:
     $$W_{\text{RBAC}, 2} = 507 + 104 = 611 \text{ операцій}$$
     *(Аналітично: $n \times 3n + 8n = 3n^2 + 8n = 3 \times 169 + 104 = 507 + 104 = 611$)*  
   *Попри подвоєння кількості користувачів, трудомісткість RBAC не зросла, а навпаки суттєво зменшилася: з 1066 до 611 (на 42.68%) завдяки укрупненню та оптимізації кількості ролей!*

3. **Порівняння моделей у нових умовах:**
   - **Абсолютна різниця трудомісткості:**
     $$\Delta W_2 = W_{\text{DAC}, 2} - W_{\text{RBAC}, 2} = 4056 - 611 = 3445 \text{ операцій}$$
   - **Коефіцієнт переваги RBAC:**
     $$K_{\text{eff}, 2} = \frac{W_{\text{DAC}, 2}}{W_{\text{RBAC}, 2}} = \frac{4056}{611} \approx 6.638 \text{ раза}$$
   - **Зниження трудомісткості:**
     $$\delta_2 = \frac{4056 - 611}{4056} \times 100\% = \frac{3445}{4056} \times 100\% \approx 84.94\%$$

---

### 1.4. Висновки щодо доцільності переходу від DAC до RBAC

1. **Асимптотична поведінка моделей:**
   - У моделі DAC трудомісткість масштабується як $O(U \cdot T)$ — квадратично відносно розмірності системи. Кожен новий співробітник, клієнт чи зміна посадових обов'язків вимагає ручного прописування привілеїв до десятків таблиць, що призводить до лавиноподібного зростання операцій адміністрування та людських помилок (забуті права, надмірні привілеї).
   - У моделі RBAC найбільш витратна частина $R \cdot T$ залежить **виключно від структури бізнес-ролей**, а не від числа кінцевих користувачів. Збільшення штату користувачів ($U$) додає лише одиничні тривіальні операції включення користувача до вже існуючої та перевіреної ролі.
2. **Ефект укрупнення ролей:**
   - Зменшення кількості ролей у 2 рази вдвічі скоротило обсяг налаштувань таблиць ($507$ проти $1014$). Це з лишком перекрило додаткові трудовитрати на реєстрацію 52 нових користувачів.
3. **Загальний висновок:**
   - У нових умовах перевага RBAC над DAC сягає **6.64 раза** (економія понад **84.9%** робочого часу адміністратора).
   - Перехід на рольову модель керування доступом (RBAC) є **безумовно доцільним, критично необхідним і економічно виправданим** для будь-яких промислових СУБД та корпоративних інформаційних систем при розширенні штату користувачів.

## Завдання №2. Проєктування системи розмежування доступу предметної області

Розмежування доступу спроєктовано на базі предметної області **«База даних меблевого магазину»**, розробленої в контрольних роботах `DB-CW-1` (UseCase-діаграма), `DB-CW-2` (UML-діаграма концептуальних класів) та `DB-CW-3` (реляційна схема БД).

### 2.1. Об'єкти, суб'єкти та ролі доступу меблевого магазину

#### 1. Об'єкти доступу (таблиці реляційної БД з `DB-CW-3`):
1. **`Client`** — дані клієнтів (ПІБ, телефон, адреса, email, дата реєстрації);
2. **`Employee`** — персонал магазину (ПІБ, телефон, посада, кваліфікація, оклад/ставка `salary`, дата найму);
3. **`Supplier`** — постачальники матеріалів та меблевої фурнітури;
4. **`Manufacturer`** — меблеві фабрики-виробники готових виробів;
5. **`Furniture`** — каталог меблів (назва, категорія, матеріал, колір, габарити, ціна продажу `price`, собівартість `cost_price`, статус наявності);
6. **`Orders`** — замовлення (дата, статус виконання, адреса доставки, підсумкова сума, зовнішні ключі на клієнта та менеджера);
7. **`OrderItem`** — товарні позиції замовлення (кількість, ціна за одиницю, проміжна сума);
8. **`Contract`** — договори на виготовлення / продаж меблів (дата, юридичні умови);
9. **`Receipt`** — фінансові квитанції про внесення оплати (дата платежу, сплачена сума, спосіб оплати).

#### 2. Суб'єкти доступу (конкретні користувачі / облікові записи в системі):
- `client_kovalenko`, `client_shevchenko` — зареєстровані покупці;
- `manager_petrenko`, `manager_ivanova` — менеджери відділу продажів та роботи з замовленнями;
- `storekeeper_bondar` — завідувач складу / працівник служби комплектації та логістики;
- `accountant_melnyk` — бухгалтер фінансово-економічного відділу;
- `admin_sys` — системний адміністратор та інженер безпеки БД (DBA).

#### 3. Групи (ролі) користувачів (RBAC-ролі):
- **`role_guest`** — неавторизований відвідувач (публічний перегляд каталогу виробів);
- **`role_client`** — зареєстрований покупець (створення та відстеження власних замовлень, перегляд своїх договорів і квитанцій);
- **`role_sales_manager`** — менеджер з продажу (прийом та ведення замовлень, формування договорів, комунікація з клієнтами);
- **`role_storekeeper`** — комірник / комплектувальник (моніторинг залишків меблів, оновлення статусу готовності виробів до відвантаження);
- **`role_accountant`** — бухгалтер (контроль оплат за квитанціями, розрахунок заробітної плати, аналітика фінансових надходжень);
- **`role_admin`** — адміністратор БД (повне керування схемою, користувачами, ролями та аудитом безпеки).

### 2.2. Рекомендації щодо вертикального обмеження доступу (Vertical Fragmentation)

**Вертикальне обмеження доступу** полягає у наданні суб'єкту прав лише на строго визначену підмножину стовпців таблиці (Column-Level Security / проекція стовпців), приховуючи конфіденційні, фінансові або службові атрибути.

| Таблиця | Роль користувача | Доступні стовпці (вертикальний фрагмент) | Приховані/заблоковані стовпці | Обґрунтування обмеження |
|:---|:---|:---|:---|:---|
| **`Employee`** | `role_sales_manager`, `role_storekeeper` | `employee_id`, `full_name`, `position`, `phone` | `salary`, `hire_date`, `qualification` | Захист конфіденційної персональної інформації про зарплату співробітників |
| **`Employee`** | `role_accountant` | `employee_id`, `full_name`, `position`, `salary`, `hire_date` | — | Бухгалтеру необхідні дані для нарахування заробітної плати |
| **`Furniture`** | `role_client`, `role_guest` | `furniture_id`, `name`, `category`, `material`, `color`, `dimensions`, `price`, `availability_status`, `production_time` | `cost_price` (собівартість), `supplier_id` | Комерційна таємниця: покупець бачить лише роздрібну ціну продажу, але не внутрішню собівартість та постачальників |
| **`Furniture`** | `role_sales_manager` | Всі стовпці, крім `cost_price` | `cost_price` | Менеджер продає за встановленою ціною, собівартість є прерогативою аналітиків і бухгалтерії |
| **`Client`** | `role_storekeeper` | `client_id`, `full_name`, `delivery_address`, `phone` | `email`, `registration_date` | Службі комплектації та доставки потрібні лише контактний телефон та адреса доставки |
| **`Receipt`** | `role_sales_manager` | `receipt_id`, `order_id`, `payment_date`, `amount`, `payment_status` | `bank_transaction_details` (реквізити рахунків) | Менеджеру достатньо факту надходження грошей без доступу до платіжних шлюзів |

---

### 2.3. Рекомендації щодо горизонтального обмеження доступу (Horizontal Fragmentation / RLS)

**Горизонтальне обмеження доступу** полягає у фільтрації записів (рядків) таблиці так, щоб суб'єкт мав доступ лише до підмножини кортежів, які відповідають визначеним предикатам та бізнес-правилам (Row-Level Security — RLS).

| Таблиця | Роль користувача | Дозволений горизонтальний фрагмент (умова відбору рядків) | Бізнес-правило та мета захисту |
|:---|:---|:---|:---|
| **`Orders`** | `role_client` | `client_id = current_client_id()` | **Принцип ізоляції клієнтів:** Покупець має доступ **виключно до своїх замовлень**. Доступ до замовлень, адрес та супреквізитів інших покупців повністю заблокований |
| **`Orders`** | `role_sales_manager` | `employee_id = current_employee_id() OR execution_status = 'нове'` | Менеджер бачить замовлення, які закріплені за ним у роботі, а також нерозподілені нові заявки для взяття в обробку |
| **`Orders`** | `role_storekeeper` | `execution_status IN ('готове до комплектації', 'комплектується', 'передано на доставку')` | Комірнику не потрібні архівні чи скасовані замовлення; відображаються лише активні складські статуси |
| **`Contract`** | `role_client` | `order_id IN (SELECT order_id FROM Orders WHERE client_id = current_client_id())` | Клієнт бачить виключно ті договори, які прив'язані до його підтверджених замовлень |
| **`Receipt`** | `role_client` | `order_id IN (SELECT order_id FROM Orders WHERE client_id = current_client_id())` | Клієнт бачить лише чеки та квитанції про власні оплати |
| **`Employee`** | `role_sales_manager` | `employee_id = current_employee_id()` *(на редагування)* | Співробітник може редагувати лише власні контактні дані |

### 2.4. Приклади SQL-реалізації обмежень у СУБД PostgreSQL

Відповідно до матеріалів лекції №14 [1], наведемо типові DDL/DCL-інструкції реалізації вертикальних та горизонтальних обмежень у СУБД PostgreSQL.

#### 1. Створення ролей та вертикальне розмежування (Column-Level Grant / Views):

```sql
-- Створення ролей за моделлю RBAC
CREATE ROLE role_client;
CREATE ROLE role_sales_manager;
CREATE ROLE role_storekeeper;
CREATE ROLE role_accountant;

-- Включення користувачів у відповідні ролі (User Assignment)
GRANT role_client TO client_kovalenko;
GRANT role_sales_manager TO manager_petrenko;
GRANT role_storekeeper TO storekeeper_bondar;
GRANT role_accountant TO accountant_melnyk;

-- Вертикальне обмеження доступу засобами Column-level GRANT:
-- Клієнт бачить лише дозволені публічні поля каталогу меблів (без собівартості)
GRANT SELECT (furniture_id, name, category, material, color, dimensions, price, availability_status, production_time)
ON TABLE Furniture TO role_client;

-- Альтернативний вертикальний захист через представлення (View):
CREATE VIEW v_public_furniture AS
SELECT furniture_id, name, category, material, color, dimensions, price, availability_status
FROM Furniture;

GRANT SELECT ON v_public_furniture TO role_client, role_guest;
```

#### 2. Горизонтальне розмежування засобами Row-Level Security (RLS):

```sql
-- Увімкнення політики безпеки на рівні рядків для таблиці Orders
ALTER TABLE Orders ENABLE ROW LEVEL SECURITY;

-- Політика для клієнтів: доступ лише до своїх замовлень за ідентифікатором сесії
CREATE POLICY client_orders_isolation_policy ON Orders
FOR ALL
TO role_client
USING (client_id = NULLIF(current_setting('app.current_client_id', true), '')::INT)
WITH CHECK (client_id = NULLIF(current_setting('app.current_client_id', true), '')::INT);

-- Політика для комірників: бачити лише замовлення на етапі комплектації чи доставки
CREATE POLICY storekeeper_orders_active_policy ON Orders
FOR SELECT
TO role_storekeeper
USING (execution_status IN ('готове до комплектації', 'комплектується', 'передано на доставку'));

-- Увімкнення RLS для платіжних квитанцій Receipt
ALTER TABLE Receipt ENABLE ROW LEVEL SECURITY;

-- Клієнт бачить квитанції лише своїх замовлень
CREATE POLICY client_receipts_policy ON Receipt
FOR SELECT
TO role_client
USING (
    order_id IN (
        SELECT order_id FROM Orders
        WHERE client_id = NULLIF(current_setting('app.current_client_id', true), '')::INT
    )
);
```
